# FitFace 가상착장(Virtual Try-On) 기능 계획

작성일: 2026-06-13
상태: 계획 확정, 구현 대기

## 0. 시작 조건

이 작업은 `redesign/editorial-black` 브랜치(오류 보완 + 디자인 시스템 변경)의
**실기기 테스트가 끝난 뒤** 시작한다. 그 전에는 구현하지 않는다.

## 1. 목표

스냅샷(매장 옷 + 얼굴 오버레이)을 찍은 뒤, 등록된 얼굴 사진과 옷 사진,
사용자의 신체 정보(키/몸무게/체형 프리셋)를 조합해 **그 옷을 실제로 입은
모습의 가상착장 이미지**를 생성해 보여준다.

기존 AI 진단(어울림 점수/비교)을 대체하지 않고, 진단 다음 단계의
"입어보기" 경험으로 추가한다.

## 2. 핵심 결정 사항

| 항목 | 결정 |
|---|---|
| 실행 환경 | **클라우드 전용**. Local Gemma는 이미지 생성이 불가하므로 지원하지 않는다 |
| 생성 모델 | **gpt-image-2** (2026-04 출시, Edits 엔드포인트로 이미지 입력 편집 지원) |
| 모델 지정 방식 | 코드에 박지 않고 프록시 환경변수 `FITFACE_PROXY_IMAGE_MODEL`로 설정, 기본값 `gpt-image-2` |
| 체형 입력 | 체형 프리셋 5종 내외 + 키/몸무게. 전신 사진 업로드는 MVP에서 제외 (Phase 3 후보) |
| 옷 영역 지정 | MVP는 수동 드래그 크롭. 자동 세그멘테이션은 Phase 2 |
| 유료화 | **이번에 구현하지 않는다.** 단, 나중에 얹기 쉽도록 이음새만 남긴다 (8장 참고) |

## 3. 노출 조건 (게이팅)

가상착장 진입점은 아래 조건을 모두 만족할 때만 활성화한다.

```text
AI 모드 == OpenAI
AND 클라우드 분석 동의 완료 (allowCloudAnalysis)
AND 프록시 URL 설정됨
AND 해당 스냅샷에 rawImagePath 존재
```

- Local Gemma / Mock / Off 모드: 버튼을 숨기지 않고 **비활성 + "클라우드 AI
  모드에서 사용할 수 있어요" 안내**를 보여준다 (기능 발견성 확보).
- 조건 판정은 provider 하나(`tryOnAvailabilityProvider`)로 모아 모든
  진입점이 공유한다.
- raw 원본이 없는 기존 스냅샷은 비활성 + "다시 촬영하면 사용 가능" 안내.

## 4. 선행 조건 — 현재 코드의 갭

| 갭 | 내용 | 해결 |
|---|---|---|
| 원본 옷 사진 없음 | `OutfitSnapshot.imagePath`는 얼굴 오버레이가 **합성된** 캡처본뿐이다. 생성 입력에는 오버레이 없는 원본이 필요하다 | 촬영 시 원본 프레임을 함께 저장하는 `rawImagePath` 필드 추가 (Phase 0) |
| 신체 정보 없음 | `UserProfile`은 얼굴 사진 3종 + 퍼스널 컬러뿐 | `heightCm` / `weightKg` / `bodyPreset` 필드 추가 (Phase 0) |

재사용 가능한 기존 자산:

- 등록된 크롭 얼굴 사진 (`UserProfile.croppedFaceImagePath`)
- `BackgroundRemovalService` 추상화 패턴 (옷 영역 추출에 동일 패턴 적용)
- `AiPromptBuilder.personalColorPromptLine()` — 생성 프롬프트에도 그대로 주입
- OpenAI 프록시의 인증 토큰 / 타임아웃 / 이미지 수 제한 / env 설정 패턴
- `AiProcessingStatus` 진행 표시 위젯

## 5. UI/UX 배치

### 5.1 진입점

| 진입점 | 시점 | 비고 |
|---|---|---|
| **스냅샷(후보) 상세 화면** (주) | 비교 화면에서 후보를 눌러 들어간 상세 화면의 액션 버튼 영역 | "가상착장 해보기" 버튼. 사진 1장 = 옷 1벌이라 멘탈 모델과 일치 |
| 촬영 직후 AI 결과 바텀시트 (보조) | 카메라 화면에서 진단 결과 확인 직후 | "이 옷 입어보기" 텍스트 버튼 → 해당 스냅샷의 착장 플로우로 이동 |
| 비교 화면 (Phase 2) | AI 비교 결과 후 | **BEST 후보에만** 바로가기 버튼. 화면 차원에서 생성 3회 유도를 막는 비용 정책. 개별 후보는 상세 화면에서 여전히 가능 |

### 5.2 신규 화면 3개

| 화면 | 역할 |
|---|---|
| 체형 프리뷰 선택 시트 | 키/몸무게 입력 + 체형 프리셋 선택. 최초 1회만 풀로 띄우고 이후엔 저장값 요약 + 수정 버튼 |
| 옷 영역 지정 화면 | 원본 사진(오버레이 없음) 위에 드래그 박스로 옷 영역 지정 |
| 가상착장 결과 화면 | 생성 이미지 + 원본 스냅샷 토글 비교, 저장/재생성, "AI 생성 이미지로 실제 착용 모습과 다를 수 있습니다" 고지 |

설정 화면 "내 정보" 항목에 키/몸무게/체형 편집 진입점을 추가한다
(체형 시트 재사용).

### 5.3 전체 플로우

```text
스냅샷 상세 → [가상착장 해보기]
→ (신체 정보 없으면) 체형 프리뷰 선택 시트 → 프로필 저장
→ 옷 영역 지정 화면
→ 생성 진행 (AiProcessingStatus 재사용, 10~30초 안내)
→ 결과 화면 → 저장 시 스냅샷에 tryOnImagePath 연결
```

## 6. 단계별 작업 계획

### Phase 0 — 기반 (클라우드 호출 없음, 단독 머지 가능)

1. `OutfitSnapshot.rawImagePath` 추가 (nullable). 촬영 시 합성 캡처와 별도로
   카메라 원본 프레임을 함께 저장. 기존 데이터는 null 허용으로 자연 마이그레이션.
2. `UserProfile`에 `heightCm` / `weightKg` / `bodyPreset` 추가 (전부 nullable).
3. 체형 프리셋 enum 정의 (5종 내외) + 선택 시트 UI.
4. 설정 화면 내 정보 편집 UI + provider 메서드.
5. 테스트: 모델 직렬화 왕복, 필드 없는 옛 JSON 로드 호환.

### Phase 1 — MVP 생성

1. 프록시에 `/ai/try-on` 엔드포인트 추가.
   - gpt-image-2 이미지 편집 호출. 모델명은 `FITFACE_PROXY_IMAGE_MODEL` env.
   - 기존 인증 토큰 / 이미지 수 제한 패턴 재사용.
   - 생성은 분석보다 오래 걸리므로 이 엔드포인트만 타임아웃 별도 상향 (예: 120초).
   - 응답 이미지가 크므로 `maxBodyBytes` 영향 점검.
2. 앱에 `OpenAiTryOnService` 추가 — 기존 `OpenAiAnalysisService` 패턴 복제
   (토큰 헤더, 타임아웃, dispose, settings 변경 시 provider 재생성).
3. 요청 구성: 크롭 얼굴 + 옷 영역 크롭 + 텍스트 프롬프트
   ("키 ○cm, ○kg, ○ 체형 인물이 이 옷을 입은 전신 사진")
   + `personalColorPromptLine()` 재사용.
4. 진입점/게이팅: 스냅샷 상세 버튼, 바텀시트 버튼, `tryOnAvailabilityProvider`.
5. 결과 저장: 생성 이미지 로컬 저장 + 스냅샷에 `tryOnImagePath` 연결.
   **같은 스냅샷+체형 조합이면 재생성 대신 저장본을 먼저 보여준다** (비용 방어 핵심).
6. 동의 문구 확장: 기존 클라우드 동의에 "이미지 생성에 얼굴 사진 사용" 명시,
   최초 가상착장 시 1회 재동의.
7. 테스트: 프록시 엔드포인트(fake client), 서비스 페이로드, 게이팅 조건별
   버튼 노출 위젯 테스트.

### Phase 2 — 품질/UX

- 옷 영역 자동 세그멘테이션 (수동 크롭은 폴백 유지)
- 비교 화면 BEST 후보 진입점
- 재생성 횟수 제한 (스냅샷당 N회) — 비용 폭주 방지
- 결과 이미지 공유/내보내기

### Phase 3 — 후보 (미확정)

- 전용 VTON API (FASHN, IDM-VTON 계열) 병행/교체 검토
- 전신 사진 입력 옵션 모드

## 7. 진행 방식

Phase 0 → 1 → 2를 **각각 별도 브랜치/사이클**로 진행한다.
Phase 0은 반나절 규모, Phase 1이 본체(프록시 + 서비스 + 화면 3개),
Phase 2는 사용 반응을 보고 결정한다.

## 8. 유료화 대비 이음새 (구현은 보류)

유료화(비회원 1회 맛보기 + 크레딧 구매)는 **별도 트랙으로 보류**한다.
현재 앱에는 계정/백엔드가 없어 "회원" 개념 자체가 없고, 크레딧 검증은
서버(프록시) 측이어야 하며, 디지털 재화는 인앱결제 의무(수수료 15~30%)가
있다는 점을 가격 설계 때 반영한다.

이번 구현에는 아래 이음새만 남긴다 (비용 거의 0):

1. **생성 요청의 길목 단일화**: 앱의 단일 서비스 메서드 → 프록시 단일
   엔드포인트. 나중에 크레딧 차감 체크가 이 한 곳에만 들어간다.
2. **프록시에 토큰별 생성 횟수 로깅**: 추후 쿼터/원장이 이 자리에 얹힌다.
3. UI에 "무료 1회" 등 정책 문구를 **박지 않는다** — 정책 미확정 상태에서
   약속이 된다.

현재의 공유 토큰 인증은 추후 "사용자별 키 + 크레딧 원장"으로 진화시킨다.

## 9. 리스크

| 리스크 | 내용 | 완화 |
|---|---|---|
| 입력 사진 품질 | 매장 진열 옷(옷걸이, 비스듬함, 가림)은 VTON 모델이 기대하는 입력과 거리가 있다 | 옷 영역 크롭 필수화. 품질이 안 나오면 Phase 3에서 전용 VTON 검토 |
| 얼굴 동일성 | gpt-image-2도 얼굴 보존이 완벽하지 않다 | "참고용 프리뷰" 포지셔닝 + 결과 화면 고지 문구 |
| 비용/지연 | 생성 1회당 실비용 + 10~30초 | 결과 캐싱, 재생성 제한, BEST 유도 동선 |
| 프라이버시 | 얼굴 사진을 "분석"이 아닌 "생성"에 전송 | 동의 문구 확장 + 1회 재동의 |

## 10. 미결정 사항

- 체형 프리셋의 구체 명칭/개수 (5종 내외로만 합의)
- 재생성 제한 횟수 N
- 결과 이미지 보관 정책 (스냅샷 삭제 시 함께 삭제 여부)
